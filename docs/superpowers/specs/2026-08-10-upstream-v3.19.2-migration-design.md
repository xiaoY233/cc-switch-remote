# Upstream v3.19.2 Migration Design

## Objective

Upgrade the fork from its current upstream v3.19.1 baseline to the exact upstream
v3.19.2 release tag while preserving CC Switch Remote product identity, release
configuration, development data isolation, and remote-management behavior.

The migration must be based on the actual upstream commits and file changes, not
only the upstream release notes. Root README files are outside the merge scope and
must remain byte-for-byte unchanged.

## Baselines and Branches

- Fork baseline: `main` at `de9d1bcb` (`v3.19.1`).
- Previous upstream baseline already merged by the fork: `28529620`.
- Target upstream release: annotated tag `v3.19.2`, peeled commit `43eaf073`.
- Upstream `main` commits after `43eaf073` are explicitly excluded.
- The local `upstream-main` branch will be fast-forwarded from `28529620` to
  `43eaf073`.
- Migration work will be performed on `codex/upstream-v3.19.2-merge`, created from
  the current fork `main` in an isolated worktree.
- The target tag will be merged with a real merge commit so future upstream
  ancestry checks remain reliable.

## Audited Upstream Change Set

The range `28529620..43eaf073` contains 26 commits and changes 114 files. The
functional change groups are:

1. Management UI and bulk actions
   - Searchable MCP, Prompt, and Skills lists.
   - Bulk per-app enable/disable actions.
   - Shared sequential bulk-action helper and localized confirmation/result UI.
2. OpenCode and OMO
   - Runtime OpenCode model loading for OMO.
   - Unified OMO configuration support.
3. Codex OAuth and usage
   - Per-account Codex OAuth quota display.
   - Correct handling of interleaved Codex token counters.
   - Batched Codex session inserts and preloaded sync cursors.
4. Backup and restore
   - Batched SQL dump inserts.
   - Single-transaction restore of preserved tables.
5. Skills
   - Resolve source directories using the `SKILL.md` anchor instead of the skill
     name.
   - Build `readme_url` from the resolved source directory.
6. Proxy and security
   - GitHub Copilot compatibility with modern Claude Code.
   - Report dropped Chat tool calls instead of synthesizing completion.
   - Bound script output, file reads, proxy bodies, and decompression.
   - Surface deep-link usage-script fields in risk review.
7. UI efficiency and layout
   - Suspend route-status animation work while the window is inactive.
   - Keep header actions visible when all applications are enabled.
8. Data and presets
   - Add Qwen3.8 Max built-in pricing.
   - Apply upstream partner preset ordering/removals/additions outside README files,
     while retaining CC Switch Remote product wording.
9. Release metadata and documentation
   - Adopt the v3.19.2 version consistently in the fork-controlled version files.
   - Import the upstream v3.19.2 release-note files as upstream reference material.
   - Preserve fork-owned release workflows and identity configuration.

Upstream-only sponsor funding changes and all root README changes are excluded.
The DeepSeek guide correction may be accepted because it documents upstream
behavior and does not replace fork product identity.

## Merge Strategy

The selected strategy is a stable-tag merge rather than cherry-picking or
rebuilding the fork on top of the upstream tree.

1. Record pre-migration hashes and fork configuration values.
2. Fast-forward `upstream-main` to `43eaf073` without including later commits.
3. Create the isolated migration worktree and establish a clean test baseline.
4. Merge the v3.19.2 tag without committing immediately.
5. Resolve explicit conflicts and audit automatically merged overlap files.
6. Restore excluded README and fork-boundary files from the fork parent where
   required.
7. Complete remote adaptations and regression tests.
8. Commit the merge, then commit any focused adaptation fixes separately when that
   produces clearer review history.
9. Run workflow-level and configuration-drift verification before reporting the
   migration as complete.

The merge preview found explicit conflicts in release workflows, fork metadata,
version files, the application shell, target-aware MCP/Prompt/Skills components,
OAuth/OMO integration, locale files, and related tests. Files that auto-merge but
overlap fork changes are treated with the same review priority as conflict files.

## README and Documentation Boundary

The following files must remain byte-for-byte identical to the fork baseline:

- `README.md`
- `README_ZH.md`
- `README_JA.md`
- `README_DE.md`

Their Git object IDs will be captured before the merge and compared after all
resolutions. No upstream sponsor, badge, screenshot, repository, or homepage change
may enter these files.

`CHANGELOG.md`, upstream guide corrections, and new v3.19.2 release-note files may
be included only as historical upstream material. They must not redefine the fork
repository, updater, product name, or release status. Existing fork remote-management
documentation must be preserved.

## Fork Identity and Release Configuration

The migration adopts version `3.19.2` while preserving these controlled values and
behaviors:

- Product name: `CC Switch Remote`.
- Cargo package: `cc-switch-remote`.
- Desktop binary: `cc-switch-remote`.
- Remote helper binary: `cc-switch-remote-helper`.
- Repository: `https://github.com/xiaoY233/cc-switch-remote`.
- Tauri identifier: `com.ccswitch.remote`.
- Deep-link schemes: `ccswitch` and `ccswitch-remote`.
- Updater endpoint: the fork GitHub release `latest.json`.
- Updater public key: the current fork signing public key.
- Application data isolation: the fork continues to use `.cc-switch-remote`, and
  development/debug data stays isolated from installed release data.
- Fork helper build, asset naming, updater manifest assembly, signing verification,
  and targeted release-maintenance workflows.

The post-merge mechanical audit compares `package.json`, `src-tauri/Cargo.toml`,
`src-tauri/Cargo.lock`, `src-tauri/tauri.conf.json`, release workflows, helper
workflows, and scripts to the known-good v3.19.1 fork state. Every difference must
be either the deliberate 3.19.2 version update, an accepted upstream improvement,
or an explicitly documented fork adaptation.

## Remote Management Adaptation

### MCP, Prompts, and Skills

The upstream search and bulk-action UI is parity functionality. Existing shared
panels remain target-aware and receive the selected `ManagementTarget` through all
nested controls and dialogs.

- Remote reads and mutations use `remoteApi` and the selected profile/secret.
- Local reads and mutations retain their original local API path.
- Cache/query keys include the target key.
- Bulk operations reuse target-aware single-item mutations sequentially.
- Successful mutations refresh only the affected target's state.
- Partial failures report localized results and do not discard prior remote state.
- Command-level failures do not close a healthy long-lived helper session.

The Rust helper remains a thin adapter over the same MCP, Prompt, and Skill services
used locally. New helper-only business logic is prohibited.

### OpenCode and OMO Models

Runtime OpenCode models are remote-adapted functionality. When the selected target
is remote, the model list and unified OMO configuration must come from that remote
host through the helper. The remote UI must not read the desktop's local OpenCode
files or invoke local-only model-fetch commands.

If the current helper interface lacks the required operation, the migration will
add a thin command over the shared Rust implementation, advertise the capability
only after implementation, and add local/remote routing tests. If support cannot be
implemented safely in this migration, the remote control must be hidden or disabled
with the existing unsupported-capability pattern.

### Codex OAuth Account Usage

Per-account quota display is remote-adapted. Local Auth Center behavior follows
upstream. A remote Auth Center must source account IDs, quota data, and errors from
the selected remote target. It must never display or query local managed-auth
accounts while a remote target is active.

### Shared Rust Improvements

Backup transactions, Codex session synchronization, Skills path resolution, usage
statistics, proxy compatibility, and security bounds are parity improvements. The
remote helper must pick them up through shared Rust services. Direct GUI SSH file
editing and duplicate helper implementations are prohibited.

Deep-link import remains a local desktop workflow. Its security review improvements
apply locally and must not create a remote browser/deep-link side effect.

## Drift Audit

For each affected remote workflow, review the visible control through its final
state source:

1. Component and nested dialog/panel props.
2. Hook and target-qualified query key.
3. API adapter selection.
4. Tauri remote command or local command.
5. Helper JSON command and capability declaration.
6. Shared Rust service and effective remote data/config path.
7. Mutation failure preservation.
8. Cache invalidation/refetch.
9. Localized success and failure feedback.

Mechanical scans will flag direct `invoke(...)` and local API calls in affected
target-aware modules. Each finding must be guarded as local-only, changed to a
target-aware adapter, or documented as unsupported.

The final report classifies affected features as parity, remote-adapted,
unsupported/local-only, fixed during migration, or still risky.

## Verification Plan

### Baseline and Merge Integrity

- Verify a clean fork baseline before merging.
- Confirm `upstream-main` ends exactly at `43eaf073`.
- Confirm the merge branch contains both fork `main` and upstream v3.19.2 as
  ancestors.
- Confirm no post-v3.19.2 upstream commit is included.
- Confirm the four root README object IDs are unchanged.

### Frontend and Target Routing

- Focused MCP, Prompt, and Skills search/bulk tests for local and remote targets.
- Tests proving remote mutations call the remote adapter with the selected profile
  and do not call local APIs.
- Tests proving query keys differ between local and remote targets.
- OMO runtime model tests for both local and remote sources.
- OAuth account/quota tests proving target isolation.
- App-shell tests covering target switching and the all-apps-enabled header state.
- Full typecheck and the relevant unit/integration suite.

### Rust and Helper

- Formatting check.
- Focused shared-service tests for backup, Skills, proxy/security, and usage changes.
- CLI/helper regression tests, including commands that return `ok: true` without
  `data` and command errors that must preserve the helper session.
- Helper no-default-features build with `proxy-runtime`.
- Full feasible Rust library test suite after focused failures are resolved.

The minimum helper-affecting verification commands are:

```text
pnpm typecheck
cargo fmt --check --manifest-path src-tauri/Cargo.toml
cargo test --manifest-path src-tauri/Cargo.toml --lib cli::tests::
cargo check --manifest-path src-tauri/Cargo.toml --bin cc-switch-remote-helper --no-default-features --features proxy-runtime
```

### Workflow-Level Checks

- Local MCP/Prompt/Skills load, search, bulk mutation, refresh, and failure message.
- Direct helper JSON workflow for the affected remote operations against an
  isolated temporary helper data directory.
- Backup creation and restore preservation behavior on an isolated database.
- Usage synchronization repeat run to verify cursor persistence and idempotence.
- Development data path remains separate from installed release data.
- Fork release/update configuration points only to fork assets and keys.

If no reachable configured remote host is available, real SSH UI-to-host validation
will be reported as unverified. Mock transport tests and direct helper execution do
not substitute for that disclosure.

## Acceptance Criteria

- `upstream-main` points exactly to upstream v3.19.2.
- The migration branch contains a real merge of the stable tag.
- All intended v3.19.2 functional changes are present or explicitly deferred with a
  reason.
- The four root README files are unchanged.
- CC Switch Remote identity, updater trust chain, helper packaging, and data
  isolation remain intact.
- Affected remote workflows use the selected remote state source and mutation path,
  refresh after mutation, preserve state on failure, and show user-facing feedback.
- Local workflows retain upstream-compatible behavior.
- Required frontend and helper checks pass, or exact failures and unverified
  workflow gaps are reported without a broad completion claim.
