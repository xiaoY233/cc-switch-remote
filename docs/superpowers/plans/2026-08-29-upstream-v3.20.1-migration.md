# Upstream v3.20.1 Migration Plan

**Goal:** Merge the exact upstream v3.20.1 stable tag into CC Switch Remote, publish the fork as v3.20.2 only after validation, and preserve local/remote state, credentials, runtime sessions, product identity, and updater behavior.

**Source audit:** [`../../research/upstream-v3.20.1-migration-analysis.md`](../../research/upstream-v3.20.1-migration-analysis.md)
**File matrix:** [`../../research/upstream-v3.20.1-file-matrix.md`](../../research/upstream-v3.20.1-file-matrix.md)

## Fixed baselines

- Fork start: `369fe9417d35d518562180b7c26fe793d61bea8b` (`CC Switch Remote v3.20.1`).
- Previous upstream baseline: `0b5da510168914b251481654a568c3ffacd62cf4` (upstream v3.20.0 peeled commit).
- Target tag object: `4a104215c4529e78c7d5e27ee47a693ada1ce2a7`.
- Target peeled commit: `3217f72596f2d1c0f879f0a05f83803825d9809f`.
- Fork release target: `3.20.2`.
- Upstream tag `v3.20.1` and fork tag `v3.20.1` are different releases. Never overwrite or push the upstream tag under the fork tag namespace.
- Do not include upstream commits after `3217f725`.
- Do not tag, push, publish, or mutate a GitHub release while executing this plan.

## Non-negotiable fork state

- Product: `CC Switch Remote`.
- Cargo package and binaries: `cc-switch-remote`, `cc-switch-remote-helper`.
- Tauri identifier: `com.ccswitch.remote`.
- Repository and updater: `xiaoY233/cc-switch-remote`.
- Data root: `.cc-switch-remote`; development and installed-release data stay isolated.
- Updater endpoint, pubkey, signature key id, asset names, Helper release tag and workflows remain fork-owned.
- Root README files retain fork identity; upstream v3.20.1 referral-link changes are excluded.
- Remote provider secrets, OAuth refresh/id tokens and third-party bearer tokens stay on the remote host.
- Helper commands remain thin adapters over shared Rust services.

## Task 3: Integrate the Codex account and OAuth model

**Primary files:**

- `src-tauri/src/proxy/providers/codex_oauth_auth.rs`
- `src-tauri/src/commands/auth.rs`
- `src-tauri/src/commands/codex_oauth.rs`
- `src-tauri/src/proxy/forwarder.rs`
- `src/lib/api/auth.ts`
- `src/components/providers/forms/hooks/useManagedAuth.ts`
- `src/components/providers/forms/CodexOAuthSection.tsx`

- [ ] Keep one injected `CodexOAuthManager` and one account store for desktop and Helper execution paths.
- [ ] Separate local account id, OIDC subject and workspace id. Same-workspace members must remain distinct local accounts.
- [ ] Migrate unprovable legacy identities to quarantine and support targeted re-login without losing provider bindings.
- [ ] Implement login epoch, cancellation and expiry checks so late device-flow completions cannot commit.
- [ ] Preserve per-account refresh locking and generation checks; reject ambiguous, stale or cross-subject token adoption.
- [ ] Derive quota, model and `ChatGPT-Account-Id` values from the bound local account's workspace mapping.
- [ ] Validate managed-provider request Bearer ownership against the bound account. A different member from the same workspace must be rejected.
- [ ] Mirror every new auth operation through `ManagementTarget → auth API → remoteApi/Helper → shared manager`. Do not let remote UI fall back to local `invoke`.
- [ ] Advertise remote re-login/cancel capabilities only after Helper implementation and tests exist.
- [ ] Verify payloads, logs, caches and desktop persistence never contain remote refresh/id tokens.

**Required tests:** same-workspace users, quarantine/targeted re-login, invalid JWT, cancelled/expired/older login flow, refresh generation conflicts, local/remote routing, selected-profile isolation and Helper secret non-persistence.

- [ ] Make `experimental_bearer_token` in the active custom provider table the only third-party Codex key projection; never write third-party keys to `auth.json`.

- [ ] Run preflight before changing the current-provider pointer, DB row, live files, takeover state or Helper runtime.

- [ ] Use one per-app `SwitchLockManager` for provider switch, takeover, Auth Center removal/logout and Helper mutations. Re-read current state after waiting for the lock.
- [ ] Use one top-level Codex transaction owner for auth, config, catalog and managed marker. Keep fork compare-and-swap guards as write preconditions, not a second rollback engine.
- [ ] Preserve a newer refresh generation for the same account during rollback; restore the original account for cross-account rollback.
- [ ] Attempt every rollback component and report all failures independently.
- [ ] Preserve the previous provider, live files, routing runtime and Helper session on command-level failure.
- [ ] Keep `EditProviderDialog` remote behavior: restore redacted secrets from the remote host and never read desktop live config for a remote target.

**Required tests:** config-only preservation on/off, unsafe legacy forms, inline/reserved tables, rejected switch leaves world unchanged, same/cross-account rollback, residual backup live projection, concurrent auth/provider operations, and actual remote filesystem assertions.

## Release decision

Release only when all of the following are true:

- the candidate contains upstream `3217f725` and no later upstream commit;
- all 74 changed files and 18 predicted conflicts have recorded dispositions;
- schema backup, migration and rollback evidence exists for desktop and Helper;
- Codex account isolation, config-only tokens and atomic rollback pass local and remote-path tests;
- fork identity, data isolation, updater, signatures, README and Helper release chain have no accidental drift;
- the installed v3.20.1 application can complete both normal and recovery upgrade paths;
- any unavailable real-SSH or platform evidence is explicitly blocking or explicitly accepted before publication.
