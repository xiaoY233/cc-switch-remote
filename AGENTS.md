# Project Rules

## Upstream Merge Policy

- Merge upstream by published release tags as the stable baseline. Treat upstream `main` commits after the latest published release as uncertain until they are included in an upstream release tag or explicitly reviewed and accepted.
- Before merging post-release upstream commits, list the commits, classify the risk, and decide whether each commit should be included, deferred, or cherry-picked.
- When a post-release upstream commit is included, record why it is safe or necessary for this fork and verify it against the local/remote management boundary rules below.
- Upstream merges must preserve fork-owned product identity and release configuration. Do not let upstream changes overwrite `CC Switch Remote` branding, Tauri identifier, deep-link schemes, app data directory behavior, updater endpoint, updater public key, GitHub repository URLs, release asset names, helper release tags, signing validation, fork-specific packaging configuration, or project-facing README identity unless the user explicitly requests that change.
- Treat version and release metadata as controlled fork state, not as ordinary upstream drift. After every upstream merge, verify `package.json`, `src-tauri/Cargo.toml`, `src-tauri/Cargo.lock`, `src-tauri/tauri.conf.json`, release notes, and GitHub workflow version/tag behavior before committing or publishing. Upstream version bumps may be used as an input, but the fork release version must be chosen deliberately.
- Before pushing any upstream merge or release-preparation commit, run a mechanical fork-config diff against the previous known-good fork release. At minimum check product name, bundle identifier, updater endpoint, updater pubkey key id, release repository, helper artifact workflow triggers, and app data directory isolation. Record any intentional change; revert accidental upstream overwrites before continuing.
- Upstream merge validation is incomplete until both functional drift and configuration drift are checked. Passing tests, successful compilation, or conflict-free merges do not prove that fork identity, updater, packaging, or release behavior stayed correct.
- Never publish a release immediately after an upstream merge based only on code tests. First verify the release chain end to end: release tag points to the intended fork commit, artifacts are named for this fork, `latest.json` targets this fork repository, updater signatures match the configured fork public key, and local-only upstream release settings have not replaced remote/fork release settings.
- After an upstream merge, search runtime code and release scripts for upstream-owned repository URLs and wrong fork aliases before publishing. At minimum scan `src`, `src-tauri`, `scripts`, and `.github` for upstream release URLs, issue-only exceptions, stale helper repos, updater endpoints, release page constants, and install script defaults. Documentation links can remain upstream only when intentionally documenting upstream.
- Treat `README.md`, localized README files, repository description copy, sponsor/referral blocks, badges, screenshots, and project homepage links as fork boundary files. Upstream documentation changes in those files must be reviewed and either adapted to `CC Switch Remote` or reverted; do not publish with upstream-facing README identity by accident.
- Do not assume a newly built version validates the existing installed-version upgrade path. Before publishing a schema-changing or updater-changing release, test or reason through the old installed app version that users currently have: startup recovery page, update check command, update install command, restart behavior, and whether those commands work before the full application state/database is initialized.
- Recovery-mode UI commands must not require application state that is unavailable in recovery mode. Commands shown before database initialization, such as database-upgrade recovery, update checks, open release page, open config folder, and quit, must either avoid `State<AppState>` entirely or use optional state via `try_state` with a direct fallback. Add a regression check when changing these commands.
- When a release or CI run fails on only one platform, do not rerun or recreate completed artifacts unnecessarily. Inspect the failed job, fix the platform-specific cause, and preserve already-valid artifacts unless the release state itself is corrupt. If a release must be deleted and recreated, state why and re-verify all assets after recreation.
- A release is not complete until the currently installed app can update through the intended user path. If the app cannot open due to database schema skew, verify the database recovery updater path specifically, not only the normal About-page updater.
- If an in-app update path is broken in the currently installed release, use a reversible recovery bridge only with explicit backups: preserve the current database, temporarily restore a compatible backup if needed, perform the in-app update, then restore the preserved database and verify the final app/schema versions.

## Upstream Merge Incident Checklist

These checks are required because the v3.17.0 upstream merge / v3.17.1 fork release exposed real failures in this fork. Do not replace this list with generic "merge carefully" wording.

- Fork release links must be verified in the actual recovery and settings UI code, not only in Tauri config. The database-upgrade screen previously opened the upstream release page because `DatabaseUpgrade.tsx` kept an upstream releases constant.
- The updater chain must be verified as a single system: `src-tauri/tauri.conf.json` updater endpoint, updater public key, generated `latest.json`, release asset URLs, signature key ids, About-page update actions, and database-recovery update actions must all point to and trust the fork release, not upstream.
- Recovery-mode commands must be tested from a state where the normal app store/database state has not been initialized. The database-upgrade updater previously failed with `state not managed for field state`; commands exposed on recovery screens must avoid mandatory `State<AppState>` or provide a `try_state` fallback.
- Development builds must be checked against the installed-app data path before and after schema changes. A dev build previously migrated the installed fork database to a newer schema and made the installed app refuse to open.
- Remote helper install paths must be checked in both GUI-generated SSH install commands and standalone scripts. `scripts/install-remote-helper.sh` previously defaulted to the wrong repository even after the helper code path used the fork.
- GitHub repository metadata is part of the fork boundary. Check `.github/CODEOWNERS`, issue templates, release workflows, helper workflows, funding links, and workflow repo arguments for upstream owner drift before publishing.
- README and localized README files are part of the fork boundary, not harmless documentation. A previous upstream merge pulled upstream sponsor/referral and project-facing README changes into the fork release; future merges must diff these files against the previous known-good fork release and keep only explicitly accepted/adapted content.
- Single-platform release failures must be repaired with targeted maintenance where possible. Do not delete or recreate valid completed artifacts just because one platform job failed; first inspect the failed job and determine whether only the missing platform/signature/latest metadata needs repair.
- A release workflow fan-out is not automatically a duplicate release, but it must be explained before publishing: distinguish app release, helper artifacts, release-note sync, and CI. If a workflow will create or mutate a release, state that explicitly in the pre-release checklist.
- Version bumps from upstream must not silently determine the fork version. Before tagging, record whether the upstream version is being adopted, incremented for fork fixes, or held back, and verify Cargo, package, Tauri, release notes, and GitHub tag all agree.
- A fork release is not ready until the currently installed older fork build can follow its real upgrade path. For this project, that includes at minimum: normal About update path when the app opens, database-recovery update path when the app cannot open, and manual release-page fallback pointing to the fork.

## Development Data Safety

- Development/debug builds must not default to the same user data directory as installed release builds. Keep development databases, stores, logs, and generated runtime state isolated unless the user explicitly opts into using production data for a specific debugging task.
- Do not run schema migrations from a development build against a user's installed-app data directory without an explicit backup and explicit user consent. A dev schema bump can make the installed app refuse to start.
- When changing app identifiers, config directory defaults, Tauri store paths, updater configuration, or database schema versions, verify that development and release data paths remain separated and document any intentional override.
- If a user reports "database version too new" or similar startup incompatibility, first identify the exact database path, stored `user_version`, app-supported schema version, and whether a dev build touched the installed-app data directory. Do not downgrade or delete the database unless the user explicitly requests that recovery path.
- Never use a successful dev run as evidence that the installed app will open. Development builds may use different schema support, different app data directories, different updater state, and different Tauri store contents. Verify the installed app's version and data path separately when diagnosing user startup or update issues.
- Treat Tauri store overrides as part of data isolation. When checking config directory collisions, inspect both the default config directory and `app_paths.json`/store overrides; a safe default does not help if a persisted override points development back at production data.

## Remote Server Management

- Treat local and remote management as separate targets. Local state remains in the local CC Switch data directory and must not become the source of truth for a remote server.
- CC Switch Remote must not mutate the upstream CC Switch app data directory in place. The remote fork defaults to its own `~/.cc-switch-remote` directory; if it needs existing upstream data, copy it into the remote directory first and migrate only the copy.
- A remote server owns its own CC Switch state, database, tool config files, MCP entries, prompts, and skills. The desktop app stores only remote connection profiles and cached health metadata.
- Build remote execution around a Rust CLI helper running on the remote host. The helper should reuse the Rust service/core logic that backs the Tauri app instead of reimplementing provider, MCP, prompt, or skill logic in TypeScript.
- Keep any NPM package as an optional installer or thin wrapper for downloading and invoking the Rust binary. Do not put durable business logic in an NPM implementation.
- Communicate with remote hosts through SSH commands that return stable JSON. Avoid editing remote files directly from the GUI through ad hoc SFTP path logic.
- Keep remote feature code isolated behind a remote adapter and remote UI shell so upstream local app changes remain easy to merge.
- Mark feature parity explicitly. Provider switching, MCP, prompts, skills, import/export, and health checks should aim for parity; tray controls, desktop deeplinks, browser OAuth flows, local terminal launch, and local proxy takeover are local-only unless a remote-safe equivalent is designed.
- Do not silently merge local and remote configuration. Any import, export, or copy between targets must be explicit, previewable, and reversible.
- Do not persist remote API keys or provider secrets in the local desktop database. Secrets should stay on the remote host unless the user explicitly performs an export or migration workflow.
- Prefer small, upstream-friendly changes: add new remote modules, commands, and UI entry points before modifying existing provider, MCP, prompt, skill, or settings flows.
- Remote helper commands must be thin adapters over shared Rust core/service logic. Do not add helper-only implementations for tool version checks, install/update commands, provider import/switch logic, MCP import aggregation, prompt management, skill management, sessions, Hermes memory, or OpenClaw settings.
- Tool environment checks and lifecycle actions must share the same Rust implementation for local and remote targets. If local behavior changes for PATH search, version classification, latest-version lookup, installer fallback, or update command anchoring, the remote helper must pick it up through the shared implementation rather than copying the change.
- Secret redaction for remote provider payloads must stay centralized. If provider schemas or secret-field detection rules change, update the shared redaction/restore path and its tests rather than adding ad hoc redaction in remote commands.
- Remote UI should reuse local page components for equivalent workflows. Add remote-specific shells only for target selection, SSH/helper status, capability gating, and host management; do not rebuild provider, MCP, prompt, skill, environment, or settings controls with separate visual patterns.
- Every new remote capability must declare whether it is parity, remote-adapted, or unsupported, and include focused tests for local/remote adapter behavior. A helper capability should not be advertised until the corresponding command is implemented and covered.
- Every remote management feature must start from a local feature parity audit. Before implementing or changing a remote feature, identify the corresponding local page, component tree, hooks, service calls, validation rules, loading states, error handling, i18n keys, tests, and user workflow. The remote implementation must document and preserve the same behavior unless a remote-specific difference is explicitly justified.
- Remote management UI must reuse the local UI structure and components for equivalent workflows. This applies to providers, settings, routing, MCP, prompts, skills, sessions, Hermes memory, environment checks, import/export, authentication, and tool lifecycle pages. Do not create visually separate, simplified, or placeholder remote pages when a local page/component already exists.
- Remote settings pages must preserve the local settings module ownership, titles, ordering, and component boundaries. Do not add wrapper sections such as "Remote General Settings" or remote-only explanatory headers to replace local modules. If a remote setting belongs to local `Settings > Routing`, it must live in the remote routing page; if it belongs to local `Settings > General`, render the matching local component or a target-aware variant and hide/disable only the truly local-only controls.
- Remote management logic must reuse local business logic through target-aware adapters, shared hooks, shared Rust services, or shared command handlers. Do not add remote-only shortcuts that skip local validation, state transitions, provider mapping, secret handling, lifecycle checks, queue updates, configuration normalization, or status refresh behavior.
- A remote feature is not considered implemented just because the page renders or a button exists. It must complete the full workflow: load remote state, display the same effective state as local, validate input, save to the remote host, refresh state after mutation, show localized success/failure feedback, handle unsupported helper capabilities, and include focused tests for the local/remote behavior split.
- For any local feature migrated to remote management, keep a support matrix in code or documentation: parity, remote-adapted, or unsupported. Unsupported parts must be hidden, disabled, or clearly explained in the existing UI pattern; they must not appear as clickable controls that do nothing or fail with low-level errors.
- Remote homepage controls must preserve the same dependency logic as local controls. If a local action requires an app-specific route, provider state, installed tool, authenticated account, or confirmed setting, the remote action must enforce the equivalent remote precondition before it can run.
- Remote feature additions must include an explicit comparison against the current upstream/local implementation during review. If upstream changes a local page or workflow later, the corresponding remote feature must be rechecked and updated through shared components where possible.
- Remote command failures must not tear down a long-lived helper session unless the transport/protocol is actually unusable. Command-level errors such as tool install failures, unsupported commands, validation failures, or `ok` responses without payload data must not close or recreate the helper session because the remote routing runtime can live inside that session.
- Remote helper JSON commands that return `ok: true` without `data` must be accepted for unit-returning operations. Add regression tests for remote commands that intentionally return no payload, especially settings toggles and routing toggles.
- Any remote runtime action that can affect existing remote state must be failure-preserving. If updating settings, providers, routing, tools, MCP, prompts, skills, sessions, Hermes memory, import/export, authentication, or plugin config fails, the previous remote state and any running remote runtime must remain intact unless the user explicitly requested a destructive action or the transport was lost.

## Remote Drift Audit Method

- Before changing any remote management feature, identify the matching local workflow end to end: UI component, hook, query key, API wrapper, Tauri command, Rust service/core function, live config side effects, refresh/invalidation behavior, toast/error handling, i18n keys, and existing tests.
- Start every drift audit from call-chain tracing, not from screenshots. Trace the user action from the visible control to the final state mutation or remote helper command. The audit is incomplete until the actual write/read target is known.
- For every remote workflow, verify both positive and negative target routing:
  - Remote target must call `remoteApi`/remote helper paths and must use the selected remote profile and secret.
  - Remote target must not call local-only `invoke(...)` commands, local config readers, local live provider readers, local proxy takeover commands, local terminal launch, local browser/OAuth side effects, local tray update, or local app data migrations unless explicitly classified as local-only and hidden/disabled for remote.
  - Local target must keep upstream-compatible behavior unless a remote-safe shared abstraction requires a small target-aware wrapper.
- Search for target drift mechanically before and after implementation. At minimum scan relevant modules with `rg` for direct calls to `invoke(`, `settingsApi.`, `providersApi.`, `proxyApi.`, `authApi.`, `usageApi.`, `subscriptionApi.`, `openclawApi.`, `hermesApi.`, `skillsApi.`, `mcpApi.`, `promptsApi.`, and component usages of auth/provider/settings panels. Confirm each call either receives `target`, is guarded by `target.type === "local"`, or is intentionally unsupported in remote UI.
- Do not treat a target-aware page prop as proof of parity. Confirm the prop is passed through every nested component, hook, query key, mutation, modal, footer, toolbar action, and background fetch. Pay special attention to dialogs and panels opened from remote pages because they often default back to local behavior.
- Do not treat helper command presence as proof of parity. Confirm the frontend uses the helper command, the helper command reuses shared Rust service/core logic, the command is advertised only after capability support exists, and the UI refreshes remote state after mutation.
- Compare validation and preconditions with the local workflow. Remote controls must preserve local dependency logic such as required provider state, app route enabled state, authenticated managed account, stored secret availability, installed tool status, routing/runtime state, and confirmation flags.
- Compare failure behavior with the local workflow. Remote mutations must preserve previous remote state on failure, keep long-lived helper sessions alive for command-level failures, show localized errors, and invalidate or refresh only the affected remote query keys.
- For managed auth, quotas, model fetch, usage scripts, provider switching, routing, and tool lifecycle actions, verify account/model/provider IDs come from the selected target. Remote views must never show or operate on local managed auth accounts, local API key placeholders, local usage cache, local live provider IDs, or local proxy takeover state.
- For local-only features, explicitly guard the entry point and every nested action. Local-only controls include tray updates, desktop deeplinks, local terminal launch, local browser-only flows, local proxy takeover, local live config reads, local startup registration, local updater/restart, and local app data directory mutation unless a remote-safe equivalent is implemented.
- Add regression tests for every confirmed drift fix. Prefer focused tests that prove:
  - remote target calls the remote adapter/helper with the expected profile/secret;
  - local target still calls the original local API;
  - remote target does not call a local-only API;
  - query keys include the target key when cached state can differ by target;
  - unsupported helper capabilities hide/disable controls instead of exposing failing buttons.
- For helper-affecting changes, run both frontend target-routing tests and Rust/helper checks before claiming completion. Use the narrowest relevant test set plus `pnpm typecheck`, `cargo fmt --check --manifest-path src-tauri/Cargo.toml`, `cargo test --manifest-path src-tauri/Cargo.toml --lib cli::tests::`, and `cargo check --manifest-path src-tauri/Cargo.toml --bin cc-switch-remote-helper --no-default-features --features proxy-runtime` when helper commands or Rust shared logic changed.
- A remote drift audit is not complete until the result states which items are parity, remote-adapted, unsupported/local-only, fixed, or still risky. Do not mark a feature complete only because the page renders, a target-aware API exists, or a helper command is registered.
